# Room-service responses grounded in process state

An expired confirmation must not reopen edits or claim a cancellation after delivery. The response now explains the attempted action using the identified order's persisted lifecycle, detailed status, available actions and pending tasks. KITCHEN_REVIEW means kitchen review; AWAITING_DELIVERY means accepted and awaiting delivery, not verified active preparation. DELIVERED rejects edits, cancellation and reconfirmation. Already-cancelled operations explain the recorded reason without claiming a new action.

The backend associates a versioned menu token with the operation returned by a successful START_SERVICE call in the same conversation. It reads the stored turn's incoming confirmation state, checks operation visibility in the current guest/stay context, and rejects missing or conflicting associations. Unversioned buttons cannot establish this identity. Their response asks for the reference without choosing the newest order. A known old order does not overwrite a new draft. The binding is explanatory only and never authorizes a domain action.

The scope classifier gains independent existingOrderAction/evidence/confidence fields to recognize written modifications and cancellations of existing room-service orders, including concrete edits. Full-message evidence and confidence are required. New requests, negations and hypothetical questions must not trigger this path. Explicit reference selection is deterministic; multiple or unknown references ask for clarification. Pending draft capture, current kitchen tasks and advertised service actions retain their existing execution paths.

Coverage includes Spanish and English state responses, old-order/new-draft isolation, unknown and foreign bindings, multiple orders, explicit references, written changes and cancellation, preservation of kitchen workflows, and a Spring conversation that starts an order then advances it through review, acceptance and delivery before using its original buttons. Existing no-tools/no-mutation assertions remain mandatory. Legacy fixture wording changes from a vague expiry notice to an explicit identification question; no existing behavioral checks are removed.

Prompt review must retain all prior anchors and rule text. The only intentional instruction addition is the independent existing-order intent classification; existing pending-step decision rules remain unchanged. Source dependencies, test fixtures and effective scope contexts change accordingly. Snapshot acceptance is local implementation review, not independent human approval.

No live model calls, WhatsApp sends, real hotel mutations, merges or deployments are part of this validation. Scripted model replies verify deterministic handling and integration, not real-model interpretation accuracy. Deployment and hosted enforcement remain pending.
