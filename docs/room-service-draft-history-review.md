# Durable room-service draft history

Cancelled drafts now explain that they were cancelled before submission and never request a nonexistent folio. Replaced confirmations explain the earlier version even after the updated order has been submitted. A cancelled historical draft cannot change a different current draft.

The backend reconstructs menu lineage from persisted completed turns and successful START_SERVICE receipts in the same conversation. It retains cancelled and replaced versions independently of the current conversation summary. It ignores failed turns, does not equate navigation with cancellation, separates explicit new drafts, and restricts operation associations to visible guest/stay operations. Unversioned or missing evidence still cannot identify a specific draft.

The agent adds nullable runtime-owned roomServiceDraftEvent metadata (NEW/CANCELLED) to its response. This field is excluded from the model's output schema and recomputed after planning: cancellation requires a real pending room-service draft, an eligible current decision, no tools, and removal of that pending draft. It is not guest-facing and does not authorize actions. The existing summary format remains unchanged. Java keeps constructor compatibility for existing callers; old valid Cancel-button turns can also establish cancellation history without the new field.

Tests cover cancellation across every issued version in Spanish/English, cancellation after entering edit mode, typed cancellation, old-version confirmation after submission, a new draft after cancellation, separate-draft isolation and missing/failed evidence. Three additional mandatory Spring conversations exercise durable turn history and verify zero process starts for cancelled drafts and exactly one for the submitted replacement. Existing coverage remains mandatory.

This is a local implementation review, not independent human approval or deployment authorization. There are no new model interpretation instructions in this change. No live OpenAI calls or real hotel mutations are required by these deterministic history checks. Hosted enforcement, live-model interpretation validation from the preceding change, and deployment remain pending.
